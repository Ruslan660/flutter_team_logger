Контекст — это бюджет

У модели нет памяти. Есть окно контекста, порядка 200 тысяч токенов, и в него входит всё: системный промпт, CLAUDE.md, история диалога, вывод каждой команды. Чего нет в окне — того для модели не существует.

Когда сессия разрастается, старое суммаризируется. Детали теряются, и модель начинает уверенно врать про то, что «помнит». Поэтому контекст я трачу как деньги: на задачу, а не на мусор.

Пример экономии: хук rtk перехватывает git, grep и ls и отдаёт модели сжатый вывод. На длинной сессии это 60–90% сэкономленных токенов, то есть буквально больше места для работы.

CLAUDE.md и AGENTS.md

Это файлы, которые агент читает в начале каждой сессии. Глобальный ~/.claude/CLAUDE.md — мои личные правила: как оформлять коммиты, чего не делать никогда. В репозитории — CLAUDE.md, который импортирует AGENTS.md: он общий для Claude Code и Codex, чтобы оба агента жили по одним правилам.

# AGENTS.md — что туда попадает
toolchain: fvm, melos, Java 17          ← нужно каждой сессии
правила: коммиты только по команде      ← защита от самодеятельности
ключи 2GIS: проверка перед сборкой      ← дорогая ошибка, инцидент 2026-07-10
роутинг: «для UI читай DESIGN.md»       ← ссылка вместо простыни

Главный принцип — progressive disclosure: в always-loaded файле лежат правила и ссылки, а тяжёлые документы читаются только когда задача их касается.

файлзачем

Всё это — обычный markdown в git. Его читают три стороны: Claude, Codex и я.

Скилл — это плейбук с триггером

SKILL.md состоит из двух частей. Описание с триггером модель видит всегда, оно короткое. Тело — пошаговый флоу с командами — читается только когда задача совпала с триггером. Опять progressive disclosure: сотня скиллов почти ничего не стоит, пока не понадобилась.

Как рождается скилл

  • Делаю флоу руками. Второй раз. Третий — и это уже сигнал
  • Прошу Claude оформить прошедшую сессию в SKILL.md: он помнит все команды и все грабли лучше меня
  • Правлю руками две вещи: триггер (когда скилл должен сработать) и антипаттерны (чего не делать)
  • Кладу в git. Скилл эволюционирует: наступили на новые грабли — дописали

Признак хорошего скилла: точное описание-триггер, конкретные команды вместо лирики и явный список ошибок. Плохой скилл — это статья. Хороший — инструкция по сборке.

MCP или скилл?

MCP-сервер = доступ

  • Инструменты и данные: живой процесс со схемами вызовов
  • dcm — статический анализ Dart-кода
  • context7 — актуальные доки библиотек
  • Нужен, когда агент должен дёргать систему, до которой иначе не дотянется

Скилл = знание

  • Текст в git, ноль рантайма, нечему падать
  • Порядок действий, команды, чек-листы
  • Версионируется и ревьюится как код
  • Дешевле по токенам и по поддержке

Правило простое: нужен доступ к API — MCP. Нужен порядок действий — скилл. Если сомневаетесь, начните со скилла: чаще всего его хватает.

Хуки: автоматика вне воли модели

Просьба «всегда делай так» живёт до первой суммаризации контекста. Хук — это код, который срабатывает сам: модель не может его забыть или проигнорировать.

# перехват команды до выполнения
git status  → rtk git status   # тот же смысл, меньше токенов

# на старте сессии
SessionStart → caveman on      # стиль ответов включён всегда

# перед коммитом
PreToolUse   → проверка правил  # запреты, которые не обсуждаются

Если поведение должно быть гарантированным — это хук, а не строчка в промпте.

Агенты: свежая голова под задачу

Субагент — отдельное окно контекста. Главный тред держит задачу целиком, субагенты делают грязную работу и возвращают короткий отчёт, а не тонну прочитанных файлов.

  • Explore — прочесать кодовую базу; моё окно остаётся чистым
  • Plan — архитектурный план до того, как трогаем код
  • Доменные агенты — по фичам приложения: каждый знает свой кусок
  • Параллельность — три независимых поиска запускаются одновременно и стоят как один

Правило оркестрации: делегируй вывод, а не решение. Решения принимает тред, у которого есть весь контекст задачи.

Вторая модель как ревьюер

Вчера Codex ревьюил спеку и код фичи, которую писал Claude. Результат: два P0 и восемь P1.

  • P0: flush() не является безопасным барьером — гонка над RandomAccessFile, который запрещает параллельные вызовы
  • P0: выгрузка отдавала живые файлы: ротация могла удалить файл прямо во время аплоада
  • P1: после чанка p99 файлы переставали парситься; циклический data отключал storage; dart:io в главном entrypoint ломал web-сборки

У разных моделей разные слепые зоны. Перекрёстное ревью стоит десять минут и дешевле любого продакшн-инцидента.

Хэндоффы: сессия конечна

Любая сессия упирается в лимит контекста. Заканчиваю большую работу — прошу агента написать HANDOFF: что сделано, что осталось, какие грабли уже найдены. Следующая сессия читает три абзаца и продолжает с места, а не восстанавливает картину по истории команд.

То же самое между агентами: Claude оставляет хэндофф, Codex его подхватывает. Формат один — markdown в репозитории.

Главное правило: переносим выводы, не переписку. Хэндофф на страницу полезнее лога на мегабайт.

Что из этого выношу

  • Спека на две страницы читается за пять минут — и правится за пять минут. Код правится за час
  • Фидбек человека и ревью второй модели ловят разное: человек — «зачем этот лимит», Codex — гонку над файловым дескриптором
  • Тест первым — это не ритуал: красный тест дважды ловил мои же ошибки до коммита
  • Атомарные коммиты дают дешёвый откат любого решения
  • Спека и план лежат в git рядом с кодом — ревьюер видит не только «что», но и «почему»

С чего начать

  • 1. CLAUDE.md в репозитории. Toolchain, команды сборки, правила. Час работы, окупается в первый день
  • 2. Один скилл на самую частую рутину: создание MR или запуск на симуляторе
  • 3. WORKLOG.md. Пять строк в конце сессии, чтобы завтра не начинать с нуля
  • 4. Ревью второй моделью для крупных фич — когда первые три пункта приживутся

Не пытайтесь завести всё сразу. Каждый инструмент появлялся у меня после конкретной боли, а не из каталога.
