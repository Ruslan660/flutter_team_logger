# Session file logs — design spec

Дата: 2026-07-22. Статус: принята, реализована (ревью Codex + человек).
Обновления после ревью: убран лимит maxSessions; ядро перенесено в
pure-Dart `team_logger`, во `flutter_team_logger` — Flutter-обвязка.

## Зачем

Логи текущей и прошлых сессий должны переживать перезапуск и краш
приложения. Пользователь жмёт «Отправить логи» в саппорте — приложение
прикладывает файлы последних сессий. Целевая интеграция — приложения
teztaxi (client/driver), но фича живёт в `flutter_team_logger` как
переиспользуемый publisher.

## Что делаем

Ядро — в `team_logger` (pure Dart, `lib/src/file_storage/`):

- `FileLogStorage` — publisher (`CustomLogPublisher<Log>` через
  `AsyncPublisherBase<Log>`), пишет записи текущей сессии в файлы.
- `FileLogStorageOptions` — лимиты и политика хранения.
- `FileLogStorage.collectFiles()` — файлы прошлых и текущей сессии для
  отправки в саппорт.

Flutter-обвязка — в `flutter_team_logger`:

- `FileLogFlushObserver` — `WidgetsBindingObserver`, дёргает `flush()`
  на `paused`/`detached`;
- example: кнопка «Send logs» → `collectFiles()` → `share_plus`.

Приложение подключает storage как ещё один publisher в `MultiPublisher`
рядом с `LogStorage` (in-memory UI) и консолью. Каталог передаёт
приложение (например, из `path_provider`) — пакеты не тянут
платформенные плагины.

## Формат файла

JSON Lines, одна запись — одна строка. Плюсы: append-only (падение
посреди записи портит максимум последнюю строку), стримовый парсинг,
человекочитаемо.

Первая строка файла — заголовок сессии:

```json
{"kind":"session","schema":1,"sessionId":"20260722T104501-a3f2","startedAt":"2026-07-22T10:45:01.123Z","meta":{"app":"client","version":"1.42.0"}}
```

`meta` — произвольная карта от приложения (версия, платформа, userId —
на усмотрение интегратора).

Запись лога:

```json
{"ts":"2026-07-22T10:45:02.001Z","seq":17,"lvl":800,"lvlName":"info","path":"app.order","msg":"...","trace":["order#3"],"tags":["net"],"data":{...},"err":"...","stack":"..."}
```

- Время — UTC ISO 8601 (локальная зона юзера может меняться в поездке).
- `data` сериализуется через `jsonEncode` с fallback `toString()` на
  несериализуемых значениях (поэлементно, чтобы одна плохая вложенность
  не убила весь объект).
- `err` — `toString()` ошибки, `stack` — строка стектрейса.

## Сессии и имена файлов

Сессия = один запуск `FileLogStorage` (обычно один запуск приложения).

Имя: `tlog_<startedAt UTC yyyyMMddTHHmmss>_<4 hex случайно>_p<NN>.jsonl`

Случайный суффикс исключает коллизию при двух запусках в одну секунду,
`p<NN>` — номер чанка ротации (см. ниже). Файлы одной сессии объединяет
общий префикс.

## Лимиты (дефолты, всё настраивается через options)

| Параметр | Дефолт | Зачем |
|---|---|---|
| `maxSessionBytes` | 2 MiB | вес одной сессии |
| `chunksPerSession` | 4 | гранулярность ротации внутри сессии |
| `maxAge` | 7 дней | старые логи бесполезны и это PII-риск |
| `maxTotalBytes` | 20 MiB | общий потолок каталога |
| `maxRecordBytes` | 32 KiB | одна запись не должна съесть чанк |

### Превышение лимита внутри сессии

Ротация чанками: сессия пишется в чанки по
`maxSessionBytes / chunksPerSession` (512 KiB при дефолтах). Текущий
файл никогда не переписывается: когда чанк заполнен — открываем новый
файл-чанк; когда чанков больше `chunksPerSession` — удаляем самый
старый чанк этой сессии.

Смысл: при переполнении жертвуем *началом* сессии, а не хвостом — для
диагностики краша важны последние события. Каждый чанк начинается с
копии заголовка сессии, поэтому метаданные переживают удаление первого
чанка.

### Retention (чистка при старте)

При инициализации, до записи первой записи, в том же async-потоке:

1. удалить сессии старше `maxAge`;
2. если каталог всё ещё больше `maxTotalBytes` — удалять самые старые
   сессии до попадания в лимит.

Отдельного лимита на число сессий нет: количество естественно
ограничено возрастом и общим весом.

Текущая сессия не удаляется никогда. Чистка — по сессиям целиком (все
чанки разом), возраст сессии — из имени файла (не mtime: бэкапы и
копирование его сбивают).

### Запись больше `maxRecordBytes`

Усекаются поля `msg`, `stack` и сериализованный `data` (в таком порядке
приоритета сохранения: stack режем первым, msg последним) с маркером
`"…[truncated]"` и флагом `"trunc":true`.

## Запись и flush

- `handle()` из `AsyncPublisherBase` сериализует записи — конкурентных
  записей в файл нет (в пределах одного изолята; другие изоляты — вне
  скоупа, задокументировано).
- Пишем через `RandomAccessFile.writeString` в append: запись сразу
  уходит в OS-буфер. Смерть процесса (краш Dart/Flutter) данные в
  OS-буфере не теряет — теряется только необработанная очередь
  publisher'а.
- `fsync` (`RandomAccessFile.flush`): после записи уровня `error` и
  выше, и по явному `flush()`. Иначе не фсинкаем — на телефонах это
  дорого по батарее и IO.
- Рекомендация интеграторам: дёргать `flush()` на
  `AppLifecycleState.paused/detached`.

## Ошибки записи

Логгер не должен ронять приложение никогда:

- любая IO-ошибка (диск полон, каталог удалён) — запись пропускается;
- после 5 подряд неудач storage выключает себя до конца сессии;
- об инциденте один раз сообщается через опциональный колбэк
  `onInternalError(Object error, StackTrace stack)` — приложение решает,
  слать ли в Sentry. Исключений наружу нет.

## API отправки в саппорт

```dart
final files = await storage.collectFiles(); // новые → старые
```

`collectFiles()` делает `flush()` текущей сессии и возвращает
`List<File>` всех живых сессий (текущая включена). Сжатие и транспорт
(share_plus, upload в саппорт-API) — ответственность приложения:
пакет не выбирает канал доставки. Example показывает эталонный путь:
кнопка «Send logs» → `collectFiles()` → `SharePlus` c `XFile` на
каждый лог-файл (шеринг в почту/мессенджер/саппорт-чат).

Читатель файлов обязан терпеть битую последнюю строку (см. формат) —
это нормальное следствие краша.

## Безопасность / PII

- Пакет не знает, что секрет, а что нет — фильтрация содержимого
  остаётся на политике логирования приложения (в teztaxi она уже есть:
  запрет secrets/PII в `data`).
- В options есть `recordFilter: bool Function(Log)` — приложение может
  отсечь записи целиком (например, чужие namespace'ы или verbose).
- `maxAge` — тоже про PII: логи не живут вечно.
- Каталог выбирает приложение; рекомендация — application support dir,
  исключённый из облачных бэкапов (логи не должны утекать в
  iCloud/Google backup).

## Pitfalls, учтённые в дизайне

| Pitfall | Решение |
|---|---|
| краш посреди записи | JSONL: страдает только последняя строка |
| два запуска в одну секунду | случайный суффикс в имени |
| перевод часов / смена таймзоны | UTC в записях; порядок внутри сессии — по `seq`, не по времени |
| лог-флуд забивает диск | чанки + потолки размера |
| длинная запись (огромный stack) | `maxRecordBytes` + усечение по полям |
| несериализуемый `data` | поэлементный fallback `toString()` |
| диск полон | skip → self-disable, колбэк, без исключений |
| чтение во время записи | `collectFiles()` сначала flush; битый хвост допустим |
| mtime сбит копированием | возраст из имени файла |
| логи в облачном бэкапе | рекомендация каталога + ответственность интегратора |
| очередь растёт быстрее записи | вне скоупа v1: очередь не ограничена, риск памяти при экстремальном флуде задокументирован |
| другие изоляты пишут в тот же файл | вне скоупа v1, задокументировано |

## Вне скоупа v1

- Сжатие (zip) и транспорт логов.
- Ограничение очереди publisher'а (backpressure).
- Мульти-изолятная запись.
- Чтение/парсинг файлов обратно в `Log` (UI прошлых сессий).

## Тестирование

Pure Dart unit-тесты с temp-каталогами и `package:clock` (fake time):
заголовок и формат строк, ротация чанков, retention по всем трём
осям, усечение записи, self-disable после IO-ошибок, `collectFiles()`
порядок и flush, толерантность к битой последней строке.
